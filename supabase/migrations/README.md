## Conventions

- One logical change per file. Generate with `npx supabase migration new <name>`
  so the timestamp prefix is correct — don't create files by hand.
- Every table gets `enable row level security` in the same migration that
  creates it, even before policies exist — RLS-enabled-with-no-policy means
  deny-all, so there's never a window where a table is unprotected.
- RLS policies for tables that depend on `private.*` helper functions are
  deliberately deferred to later, dedicated migrations (`_rls_policies_*`)
  because the helpers themselves depend on those tables existing first —
  see 20260815120014's header comment.
- RLS policies and `private.*` helper functions are migrations too, not
  dashboard edits.
- Reference data (permissions catalog, role templates, plans/features) is
  seeded via idempotent `insert ... on conflict do update` inside the
  migration itself, because it must exist in production too — not via
  `seed.sql`, which is local/staging demo data only.
- Review every file before committing, including anything generated by
  `supabase db diff` — the diff can miss RLS policies.
- Apply with `pnpm db:push` (needs `pnpm db:link` once, which prompts for
  the DB password — never paste that password, or any Supabase key, into
  chat/logs).

## Changing a role template or the permission catalog (Faz SAAS.1E.1)

A tenant gets a _copy_ of a role template when its default roles are
provisioned (`private.provision_default_roles`, called by
`create_tenant_with_owner`). Changing `role_templates` /
`role_template_permissions` later therefore never reaches roles that already
exist — which is how one production tenant's Salon Sahibi ended up holding
19 of the 23 permissions. So any migration that changes a template's
permission set, adds a permission key, or otherwise touches `role_templates`,
`role_template_permissions` or `permissions` must:

1. Keep the SALON_OWNER template equal to the ENTIRE permission catalog (a new
   key needs its `role_template_permissions` row for SALON_OWNER in the same
   migration; `tests/system-role-drift.test.ts` fails otherwise).
2. End with `select * from private.sync_pristine_default_roles();`. It adds the
   missing keys to every _pristine_ system-default role (`customized_at is
   null`), writes one `role.template_synced` audit row per role changed, and
   never removes anything. Roles an unrestricted owner customized through
   `update_role_permissions` (that is what sets `roles.customized_at`) and
   owner-created custom roles are never touched.
3. If the change TIGHTENS a template (takes a key away), scope the removal to
   that template: `select * from
   private.sync_pristine_default_roles(null, true, '<TEMPLATE_KEY>');`.
   Removal is opt-in and never the default.
4. Never edit existing tenants' `role_permissions` rows by hand in a
   migration — the sync is the audited path, and the only one that respects
   `customized_at`.

A migration that skips step 2 fails `tests/system-role-drift.test.ts`. To see
where the live roles stand against their templates (read-only):

```sql
select * from private.role_template_drift()
where drift_state not in ('in_sync', 'customized_in_sync');
```

`pristine_missing` / `pristine_extra` are what the sync repairs;
`customized_drift` is an owner's deliberate choice and is only reported.

Adding a fifth primary role: set `role_templates.provision_by_default` (and
`display_order`) for it and end the migration with
`select private.provision_default_roles(id) from public.tenants where
deleted_at is null;` (idempotent), then the sync.

## Lessons (read before adding more `private.*`-calling RPCs)

`private` has `usage` revoked from `authenticated`/`anon` (20260815120014) —
only `SECURITY DEFINER` functions can reach into it, because a definer
function runs with the _owner's_ privileges, not the caller's. The
`public.*` wrapper functions in 20260815120019 (needed because PostgREST/RPC
only exposes the `public` schema — see that migration's header) were
originally `security invoker`, which meant every RPC call — including
`create_tenant`, i.e. onboarding — failed with `permission denied for
schema private`. Caught by the cross-tenant isolation test suite, not code
review; fixed in 20260815120020. Any new `public.*` wrapper around a
`private.*` function must be `security definer`.

## Customer notifications (Faz NOTIF.1A: the appointment-confirmation email)

The outbox (`private.customer_notification_jobs`), the per-tenant activation
switch (`private.customer_notification_activation`) and the booking-time
recipient snapshot (`private.appointment_booking_contacts`) live in `private`
with RLS on and every table privilege revoked; the worker reaches them only
through four `service_role`-only `public.*` wrappers. A new customer channel or
type (reminder, cancellation, ...) extends the CHECK vocabularies and the
activation rows — it does not get a new table, and it never reuses the Web
Push outbox (`notification_*`), which is membership/device shaped and globally
gated.

- Hooks into the booking and status flows are thin and swallow their own
  errors (a `raise warning` with the SQLSTATE only): a booking or an approval
  must never fail because of an email. The booking hook wraps only the small
  PUBLIC `create_guest_booking` wrapper and carries a drift guard that refuses
  to overwrite anything but the plain pass-through it was written against.
- A feature is switched on per tenant by the operator (SQL editor), never by
  application code; there is no row = off default, and a watermark so nothing
  historical is ever sent. See `private.activate_customer_confirmation_email`.
- Real SMTP is reachable only when `VERCEL_ENV` is `production`
  (`lib/email/smtp-transport.ts`); tests and local runs can only reach a
  loopback catcher (`tests/smtp-catcher.ts`).
- A new `service_role` function grant is a reviewed event: add it to
  `SERVICE_ROLE_FUNCTION_WHITELIST` in `tests/security-grants-regression.test.ts`
  AND to the two baseline pins in `tests/customer-reschedule.test.ts` and
  `tests/customer-cancellation.test.ts`, with the reason. A new `vercel.json`
  cron entry is pinned the same way in `tests/notification-purge-endpoint.test.ts`.

## Guided onboarding — one readiness read model (Faz LAUNCH.1C)

`20261024090000_guided_onboarding.sql` adds eight functions and nothing else: no table, no column, no trigger, no policy,
no grant on an existing object, no data.

- **One source of truth.** `private.onboarding_status(tenant)` derives everything from the real tables on every call:
  which setup step is done, which blockers remain (`tenant_inactive`, `salon_profile_missing`, `no_working_hours`,
  `no_services`, `no_staff`, `no_bookable_staff`, `public_booking_disabled`, `no_available_slot`), and `ready`. "Ready" is
  not "rows exist": a probe walks the next 14 days with the SAME predicate the public slot picker uses
  (`private.staff_is_available` plus the capacity check) and only a real bookable time makes a salon ready. Nothing is
  stored, so nothing can drift, and a salon configured the old way is simply ready without ever seeing the wizard.
  The application never recomputes readiness (`lib/modules/onboarding/model.ts` only validates the shape of the answer).
- **Writes reuse the existing tables and permission keys** (`settings.manage`, `services.manage`, `staff.manage`,
  `schedules.manage`): `update_salon_profile` (name, explicit time zone and currency, primary-branch phone/address),
  `onboarding_add_services` (<= 50, atomic, idempotent by name), `onboarding_add_staff` (roster only, never a login or an
  invitation), `onboarding_apply_weekly_hours` (one template to chosen people; a repeated weekday is a break),
  `onboarding_set_staff_services` (the staff x service matrix). All are `authenticated` only (explicit revokes from every
  other API role), tenant-scoped through `private.has_permission(p_tenant_id, ...)`, audited, and serialised per tenant.
  Pinned era-aware in `tests/security-grants-regression.test.ts`. No `service_role` function is added.
- **Error codes** `OB010` not signed in, `OB011` not allowed, `OB012` invalid input, `OB004` salon not active.
- **A multi-block weekday** (a lunch break) is one row per block. The per-person schedule editor can only show one block
  per day, so it now displays such a day read-only and saves it back unchanged (`tests/launch1c-schedule-tab.test.tsx`).
- Release order: migration first, application second. Rollback: `LAUNCH-1C-ROLLBACK.sql` (reference; drops the eight
  functions and restores the previous function catalog exactly, proven on a scratch database).
- **Booking engine vs onboarding readiness.** The status carries both `bookingEngineReady` (a real slot can be produced:
  no `tenant_inactive`, `no_working_hours`, `no_services`, `no_staff`, `no_bookable_staff`, `no_available_slot`) and `ready`
  (the engine PLUS a complete profile with a salon phone and the public switch). The slot probe never looks at the phone, the
  switch or the profile. Probe candidates sit on the same 15-minute grid, counted from midnight, as the public slot picker.
  This function is the authoritative readiness definition; the older panel "Attention" card is known P1 tech debt and no
  second definition may be added.

## Customer appointment notifications — the lifecycle (Faz LAUNCH.1B)

`20261023090000_customer_notification_lifecycle.sql` extends the NOTIF.1A/1B outbox; it does not add a second one.

- **Four types** (`appointment_confirmation`, `appointment_update`, `appointment_cancellation`,
  `appointment_reminder_24h`), each an independent per-salon switch in `private.customer_notification_activation`.
  No row = OFF, for every salon, including every existing one. The Owner (`settings.manage`, which the locked default
  roles give to the Owner only) flips them through `get_/set_customer_notification_setting` and reads a PII-free
  `get_customer_notification_health`; each real change writes an audit event. These three RPCs are `authenticated` only
  (never anon, never service_role) and are pinned era-aware in `tests/security-grants-regression.test.ts`.
- **Dedupe**: the key is now (appointment, type, channel, `dedupe_revision`). Confirmation and cancellation stay at
  revision 0. An update takes the next revision per change (changes made while one is still queued are coalesced into it,
  90 s debounce). A reminder's revision is the appointment start in epoch seconds: one reminder per appointment per start.
- **Reminder rule** (`private.materialize_customer_reminders`, run at the start of every claim, instant arithmetic only, so
  the salon timezone only matters for how the time is WRITTEN): created when the start - 24 h moment has arrived and is at
  most 3 hours old, the appointment is confirmed, a recipient exists, the switch is ON, and the last schedule change
  (`private.appointment_schedule_anchor.set_at`) happened BEFORE that moment. An appointment booked or moved less than
  24 h before its start therefore never gets a "tomorrow" reminder; a missed window is skipped, not sent late.
- **Claim-time re-validation** for every type against current state (switch still ON, tenant active, recipient,
  confirmed / cancelled as the type requires, still in the future, reminder start unchanged and inside its window, job not
  older than 48 h). A switched-off tenant's queued jobs are simply not handed out; history is kept.
- **Recipient snapshots** are now also captured for staff-created appointments (the customer record's address at creation,
  immutable), only while a switch is ON, and live until the appointment ended plus the retention window.
- Release order: migration first, application second. Rollback: `LAUNCH-1B-ROLLBACK.sql` (reference, proven on a scratch
  database to restore main's catalog exactly; it deletes only the new notification types' rows).
