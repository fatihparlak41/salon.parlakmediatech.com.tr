# Migrations

Empty on purpose — Faz 0 sets up structure only, no business schema yet
(see project root `README.md`, "Fazlar").

Faz 1 adds the first migrations here, in order, roughly:

```
0001_create_tenants.sql
0002_create_profiles.sql
0003_create_branches.sql
0004_create_permissions_catalog.sql
0005_create_role_templates.sql
0006_create_roles_and_role_permissions.sql
0007_create_tenant_memberships.sql
0008_create_platform_admins.sql
0009_create_plans_features.sql
0010_create_subscriptions.sql

0012_create_audit_logs.sql
0013_create_private_helper_functions.sql
0014_rls_platform_tables.sql
0015_rls_tenant_tables.sql
```

Conventions (once Faz 1 starts):

- One logical change per file. Generate with `npx supabase migration new <name>`
  so the timestamp prefix is correct — don't create files by hand.
- RLS policies and `private.*` helper functions are migrations too, not
  dashboard edits.
- Reference data (permissions catalog, role templates, plans/features) is
  seeded via idempotent `insert ... on conflict do update` inside the
  migration itself, because it must exist in production too — not via
  `seed.sql`, which is local/staging demo data only.
- Review every file before committing, including anything generated by
  `supabase db diff` — the diff can miss RLS policies.
